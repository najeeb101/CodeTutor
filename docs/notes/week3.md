## 1. What we built

## 2. Key design decisions and trade-offs

<!--
Raw facts (pick 3-4; for each: the choice, the alternative, what it costs):
- Postgres as the queue, not Redis + RQ/Arq (a change from the brief). Saving a submission and
  queueing it are ONE insert, so a job can't be lost between two systems ("dual write"). Cost:
  we wrote ~100 lines of claim/lease/retry SQL ourselves; Postgres is not built for huge queue
  throughput (fine for thousands of jobs per minute, not millions).
- Two problem tables: `problems` (student view, the API reads only this) and
  `problem_versions` (full sealed copies, only the worker reads them). A wrong API query can't
  leak hidden tests. Cost: the hidden tests are still in the same database; only a test
  guards the API code until there is a separate database role.
- `json`, not `jsonb`: measured, jsonb turned the float 1e300 into an int and 1E2 into 100. The
  grader treats 30 and 30.0 differently, so storage must not change numbers. Cost: no indexed
  search inside those values (we don't need it).
- At-least-once grading with an idempotent save: a job can be GRADED twice (a lease ran out),
  but the result is SAVED once (fencing token). This is the honest guarantee of any queue.
- 202 Accepted + polling, not a request that waits 1-38 s for the grade. Cost: one small
  query per second per waiting student.
- The API sends Python's repr text ("32.0", "'Fizz'", "None") for everything a student sees,
  because JavaScript has one number type: JSON.parse("32.0") is 32.
- Rate limits in Postgres with SELECT ... FOR UPDATE on the user's row: without the lock,
  12 of 12 concurrent submits got in with a limit of 5.
- Dev login = just a name (X-User-Id header). NOT secure; one function (`current_user`) is the
  only thing real auth has to replace.
- Monaco served from our own server, not a CDN; telemetry off (FastAPI's OpenTelemetry
  auto-setup, Next.js usage data); Next's auto-written AGENTS.md/CLAUDE.md turned off.
-->

## 3. Hardest bug / surprise and how we fixed it

<!--
Raw facts (pick 1-2 and tell them as a story: what you saw, what you suspected, how you found
the cause, what you changed, how you proved the fix):
- A lone surrogate ("\ud800") in a request crashed the API with a 500: FastAPI's default 422
  answer copies the bad input back, and Starlette's UTF-8 encoding can't encode it. Found by a
  test. Fix: our own 422 handler (no input echo, ASCII-escaped JSON).
- The race test proved the lock matters: removing it let 12 of 12 submits through (limit 5),
  in 3 of 3 runs; with it, exactly 5 in 10 of 10 runs.
- jsonb silently rewrote numbers (1e300 became a 301-digit int). Found by round-tripping real
  values before choosing the column type.
- WSL mirrored networking: a connection to a port nobody listens on waits for a timeout
  instead of being refused. It made a stopped database hang > 2 min (fix: connect_timeout
  5 s), and made the browser check take 47 s (probes without a timeout; fix: 1 s limits). The
  rest of that time was deleting Chrome's profile through WSL's file bridge (~12 s; fix: let
  Windows delete it). 47.5 s → 17.4 s.
- JavaScript turned the float 32.0 into 32 on the very first problem (celsius_to_fahrenheit):
  the UI would have taught the wrong type. Fix: the API sends Python repr text.
- Next.js 16.3's dev server wrote AGENTS.md and CLAUDE.md (AI-agent instructions) into web/
  without asking. Turned off with `agentRules: false`.
- Port 3000 was already taken by another dev server on the laptop (listening on all network
  interfaces); our server failed loudly (EADDRINUSE), so the UI moved to 3100.
-->

## 6. If I had more time / at Scale's scale, I would…

<!--
Raw keywords (pick 3-4, and say WHY each one matters):
- Real authentication (and a per-IP limit): today anyone can be anyone, and new names are free.
- A separate database role for the API without access to `problem_versions`, so the database
  itself refuses a leak of hidden tests.
- Push instead of polling: Postgres LISTEN/NOTIFY to wake workers, Server-Sent Events to the
  browser.
- Autoscale workers on queue depth, and fair scheduling across users (not only per-user limits).
- A stronger sandbox: gVisor or Firecracker (containers share the host kernel).
- Observability: queue depth, grading latency p50/p95, failure reasons per worker; alerts.
- An idempotency key on submit, so a retried request never creates two submissions.
- A request-size limit at the reverse proxy (uvicorn reads the whole body first).
- Generated TypeScript types from the OpenAPI schema; a browser test in CI.

## 7. Five likely interview questions (and my answers)

**5. How do you test the whole system end to end, and what does each layer catch that the others don't?**
